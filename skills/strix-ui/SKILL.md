# Strix ui

Establish whether the user requested implementation, review, polish, workflow
changes, or a shared-component migration. Keep review read-only unless repairs
are authorized. Read applicable instructions and the project's design-system
references, then inspect target source, shared primitives, and sibling flows.

Trace the user's entry, action, result, and recovery before choosing layout or
navigation. Compare the same concept across related pages. Preserve domain,
permission, mutation, and cache boundaries when consolidating presentation.
Do not turn a local improvement into a design-system migration.

Choose existing primitives and semantic tokens before adding local decoration.
Read unfamiliar component contracts. For a shared change inspect representative
consumers, defaults, and compatibility; coordinate required migrations within
authorized scope. Use established dependencies and conventions. Do not mandate
a framework, token vocabulary, color space, or motion library.

Design the relevant loading, empty, error, disabled, success, overflow, and
narrow-layout states along with the resting view. Preserve keyboard access,
focus entry and return, accessible names, visible validation, and reduced-motion
behavior. Keep status and selection distinct from neutral decoration. Name
consequential user actions clearly.

For a supplied visual reference, inspect the actual artifact and record its
identity and viewport; do not reconstruct it from memory. Use rendering when
source cannot settle a visual decision. Defer formal browser proof until
implementation and review repairs settle, then exercise only affected acceptance
states through the project verifier or strix-verify-web when installed.

For a visual claim capture the actual rendered result. Keep before/after
captures comparable in viewport, theme, fixture, and state; sanitize identifying
data. If no truthful baseline exists, label the result after-only. Report the
changed behavior, validation, rendered evidence, and material limits.
