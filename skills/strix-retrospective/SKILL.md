# Implementation retrospective

Use the completed session to identify lessons that could improve future work.
A successful result may be: "No skill changes recommended from this implementation."
Do not manufacture findings, fill a quota, or treat elapsed effort alone as a defect.

## Timing and scope

Run after the requested implementation, validation, review and any authorized
publication or shipping are complete. An inner implementation skill defers to
the outer delivery owner. Do not delay an unfinished task to produce a retrospective
or describe blocked work as complete. An explicit request for lessons may reflect
on incomplete work, with that limitation stated.

Use existing session observations, errors, receipts and user feedback. Do not
start a new bug hunt, broad skill audit, browser drive, benchmark or subagent.
Read only the relevant owner instructions needed to verify a potential lesson.
For resumed work, use retained evidence and state uncertainty about missing history.
If the workflow is extended later, report only new lessons since the prior reflection.

## Evaluate a lesson

For each candidate, establish what actually happened and its consequence, such
as a failed prerequisite, repeated check, lost browser ownership or unclear handoff.
Read the current skill or reference that owns that decision before proposing a change.

Distinguish an instruction gap or conflict from an agent overlooking a clear rule,
an environmental failure, or a safeguard doing its job. An execution mistake does
not by itself justify another rule. A useful check catching a defect may belong
earlier in the workflow; do not remove it just because it failed.

Recommend the smallest adjustment in the existing owner. Avoid duplicate rules,
new approval gates, blanket test requirements and special cases that lack a reusable
need. Keep authorization, tenant, migration, recovery and evidence safeguards intact.
State any tradeoff or uncertainty that matters to the proposed adjustment.

## Report and authority

Keep the normal completion summary first. Then briefly state each worthwhile
lesson with its observed evidence, the responsible skill or reference, and the
proposed adjustment. Link the owner when available. Use only as many proposals
as the evidence warrants; a longer list needs distinct consequences, not a target count.
If nothing warrants a change, say so in one sentence. Do not repeat known lessons
already addressed in the current work.

This skill is read-only. Do not edit skills, create a backlog, open issues, commit
or publish lessons automatically. The user may approve, reject or refine individual
proposals in a later response. That approval applies only to the identified changes,
not future retrospectives or unrelated lifecycle actions. Existing explicit authority
for implementing approved lessons is handled by the appropriate editing workflow;
reflection itself does not reopen or expand it.
